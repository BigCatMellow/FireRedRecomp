## Standing principle: keep modding cheap later, without building it now (2026-08-17)

The full mod API (Phase 10) is deliberately deferred until there's an actual
game to mod against — designing a loader/registry/versioning system now,
against content that doesn't exist yet, would just mean reshaping it later
anyway. But a few architectural habits are cheap to hold to now and
expensive to retrofit after hundreds of files assume otherwise. Apply these
as ongoing constraints on Phase 3-9 work, not as a new task:

1. **Story/map gating always routes through the real flag/variable system,
   never an ad hoc Lua boolean.** Real FireRed's own story is already
   flag/var-driven (`FLAG_BADGE01_GET`, `VAR_*`, script conditionals) — that
   existing design is *why* a future mod could plausibly go "open world"
   just by shipping different scripts/flags, with no engine changes. If
   this project ever hardcodes a story gate as a one-off Lua condition
   instead of reading the same flag/var mechanism the ROM itself uses, that
   door quietly closes. Every new story/quest/warp-gating decision should
   be checked against this.
2. **Engine logic stays content-agnostic; real FireRed specifics live in
   data tables, not control flow.** `BattleEngine.lua` already doesn't know
   what a trainer or a wild Pokémon is — just battler tables (see its own
   header's repeated "party-agnostic" framing). That discipline is the
   whole mechanism that would let a mod's new move/species/map run through
   the same engine someday. Keep extending it: real IDs/values belong in
   imported data or test fixtures, not baked into engine logic that doesn't
   need them for correctness.
3. **ROM-imported tables are one data source behind a stable shape, not the
   only possible one.** Every `import/*.lua` module's real job is "raw
   bytes -> this project's canonical shape for species/moves/maps/scripts/
   etc." A future mod source supplying a *replacement* table in that same
   shape shouldn't require reshaping every consumer — so keep import
   modules honest about that boundary (parse-into-shape, not
   entangled-with-where-the-bytes-came-from).
4. **Save-compatible data layers stay separate from the UI built on them.**
   Already the pattern (`PcBoxes`/`SaveFileCodec` vs. whatever UI
   `main.lua` wires on top, `PokemonMart.lua` vs. `PokemonMartMenu.lua`).
   A mod that reskins/overhauls a UI (e.g. the PC) then only touches the UI
   layer; changing the save format itself is a separate, harder,
   Phase-10-style compatibility problem, not something UI work should ever
   accidentally force.

None of this changes what gets built in Phases 5-9, only how — flag these
during review if new code violates one of them.

**Audit finding, fixed (2026-08-17)**: `EarlyStory.lua`'s `removedLabObjects`
table duplicated real object removal (real FireRed's `removeobject`/
`removeobjectat` script opcodes, which both set the object's own hide flag
AND despawn it live without a reload) as a one-off table hardcoded to
Oak's Lab, instead of the general script-VM primitive real content
actually uses. Fixed: `removeobject`/`removeobjectat` (opcodes 0x53/0x54)
are now real, decoded, dispatched opcodes (`ScriptBytecode.lua`/

NOT where this lives; this is field/script infrastructure, Phase 5's
scripting layer. `EarlyStory.lua` itself is intentionally left alone (a
bespoke abbreviated-cutscene controller that doesn't run through the
script VM), but any future script-driven story content can use the real
primitive instead of reinventing this pattern.
