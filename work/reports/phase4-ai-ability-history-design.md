## Source ownership and lifecycle

`struct BattleHistory` has `abilities[2]` indexed by side, not by party member or active battler (`pret/include/battle.h:295-302`). `SetUpBattleVars` calls `BattleAI_HandleItemUseBeforeAISetup` (`pret/src/battle_controllers.c:41-60`), which zeros the **whole** history and copies trainer items before calling `BattleAI_SetupAIData` (`pret/src/battle_ai_script_commands.c:262-286`). The latter also performs the four simulated-damage RNG draws during setup, and the opponent subsequently calls it again for each move choice (`:289-310`; `pret/src/battle_controller_opponent.c:1350-1359`). Initialization's RNG is a separate whole-battle parity issue; do not silently introduce new draws under an ability-history change without an approved RNG/replay design.

`RecordAbilityBattle(battler, ability)` writes only when `GetBattlerSide(battler)==0` (player); it overwrites `abilities[0]` with the supplied ID, including zero if supplied (`pret/src/battle_ai_script_commands.c:481-485`). It consumes no random value and does not compare species. All source-wide references to `BATTLE_HISTORY->abilities` are that write and the AI reader at `:1151-1153`; no switch, forced replacement, faint, or enemy replacement clears it. Therefore even a prior player's revealed ability remains authoritative after switching to another species until overwritten; this is source behavior, including apparently stale knowledge. Fresh battle setup clears it. Foe-side record calls have no effect.

Local `BattleEngine.new` owns one battle (`local/src/core/BattleEngine.lua:1318-1334`); voluntary and forced switches replace battler objects while retaining the engine (`:4237-4262,4833-4849`). A conceptual history value belongs on the **battle instance**, initialized before `resolveBattleStart` and retained through both forms of replacement, not on a battler, party/save record, controller message, or foe orchestrator. Controller runs switch-in effects during construction (`local/src/core/BattleSceneController.lua:147-157`). The current runtime has no equivalent ability-history storage.

## Reader and RNG

`Cmd_get_ability` chooses user/target battler, then tests its **side**, not its role name; `AI_TARGET=0` equals `B_SIDE_PLAYER=0` (`pret/include/constants/battle_ai.h:5-8`, `pret/include/constants/battle.h:37-38`; `pret/src/battle_ai_script_commands.c:1138-1195`). For a player-side target, strict precedence:

1. Nonzero player-side history: return that recorded ID, no draw, even if stale or differing from current actual/species abilities.
2. Otherwise actual Shadow Tag, Magnet Pull, Arena Trap: return actual, no draw.
3. Otherwise look up **current battler's species** in `gSpeciesInfo`. If ability 0 nonzero and ability 1 nonzero, draw `Random()%2` on **each query**: odd returns ability 0, even returns ability 1; no guess is saved. If ability 0 nonzero and ability 1 zero, return ability 0 without a draw. The odd fallback with ability 0 zero returns ability 1 without a draw; source comments say valid species cannot have only ability 1. For opponent-side battlers return their actual ability without a draw.

`local/import/SpeciesInfo.lua:47-78` imports two ability IDs; `local/src/core/BattlePartyBridge.lua:124-150` resolves the actual selected ability and species but does not preserve both choices on the battler. `local/main.lua:1498-1502,1539-1559,1568-1570` holds `catalog.species` when constructing the ordinary trainer battle; however, `TrainerAI.choose(engine, flags)` currently receives neither species table nor history (`local/src/core/TrainerAI.lua:137-150`). An eventual narrow context could pass a read-only species lookup plus the battle-owned history to the Brock-specific AI route; a different valid design is immutable per-battler base ability pairs correctly supplied on each switch. Both need a separately authorized owner/bridge design and explicit invalid/missing-species behavior. Never substitute the battler's actual ability for an unknown two-ability guess; never cache the guess or use a single draw for two calls. Preserve Oak-lab `EarlyRivalAI` behavior/routing; ordinary existing flags 0 and 1 should not silently change.

RNG oracles (assume valid player-side species abilities [11,22], current actual neither trapping ability): no recorded history and successive values 3, 4 -> answers 11,22 and two draws; recorded 33 -> answer 33 with zero draws regardless of actual/species; actual trapping ability with no history -> actual with zero draws even if two species abilities; historical 33 beats a current trapping ability and still draws zero; one ability [11,0] -> 11, zero draws. Record of foe-side 44 leaves history unchanged, record of player 44 overwrites 33; switch with no triggering record retains 44, while player-side switch-in recording 55 replaces it; a fresh battle clears it. To test precedence use synthetic values independent of ROM.

**Design conclusion:** the local guard crosswalk is now complete for the scoped rg inventory, but broad source-faithful Brock history has the concrete unmodeled ability-record producers and conditions above. An exact modeled-only history/lookup slice could be specified separately with explicit preconditions, but this report does not grant a file allowlist or claim live source parity while those prerequisite mechanics remain unrepresented. No isolated ability implementation is permitted to manufacture absence of Wonder Guard or other source mechanics; retain the current Oak-lab path and loud boundaries until an independently reviewed task resolves them.
